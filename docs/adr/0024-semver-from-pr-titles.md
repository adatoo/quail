# ADR-0024: SemVer from PR titles, bumped in every PR, released on every merge

**Date:** 2026-09-23 · **Status:** Accepted

> **Amended by ADR-0031 (2026-09-24):** releases are no longer marked pre-release while 0.x — GitHub's `releases/latest`, which Sparkle and Homebrew rely on, skips pre-releases.

**Decision:** Quail's version is SemVer, kept in `project.yml` (`MARKETING_VERSION`, plus `CURRENT_PROJECT_VERSION` as a build number that rises with every release). Every PR carries its own bump, derived from its Conventional Commits title — `feat` → minor, other types → patch, `!`/`BREAKING CHANGE` → major (minor while 0.x) — made with `scripts/bump-version.sh` and enforced by the required `version` check. PRs merge only with merge commits (no squash, rebase, force-push or direct push; admins included) and auto-merge once `build-and-test` and `version` pass. Every merge to `main` tags `vX.Y.Z` and publishes a GitHub Release from that version's CHANGELOG section (pre-release while 0.x); the signed DMG is attached once signing is configured (`vars.SIGNING_ENABLED`).
**Alternatives:** Bumping at release time on `main` (release-please style) — needs a bot to push to `main`, which "PRs only" forbids. A label per PR — one more thing to forget; the title is already required to be Conventional. Squash merges — the user chose merge commits.
**Why:** User request: SemVer releases, a bump in every PR, auto-merge on green CI, and a `main` that only changes through merged PRs. Computing the bump from `main`'s version inside the PR keeps `main` untouched by bots and makes every merge commit a releasable version.
**Trade-off:** Two open PRs conflict on the version lines once one merges; the second re-runs the bump script (the check says so). Anything automated that pushes or merges needs a token that isn't `GITHUB_TOKEN` (*ADR-0046: a GitHub App's, no longer a PAT*) because actions taken with `GITHUB_TOKEN` start no workflows — without it, Dependabot PRs need a manual bump and auto-merge must be enabled by hand.
**Revisit if:** PR volume makes version conflicts routine (a merge queue would serialize them), or Sparkle needs a different build-number scheme.
**Amended 2026-10-06, the bump is the last commit, alone:** every branch ends with one commit that holds only the version bump and its CHANGELOG entry (`project.yml`, `Quail.xcodeproj/project.pbxproj`, `CHANGELOG.md`, typically `chore(release): bump version to X.Y.Z`), after the work's own commits. This is the rule across the maintainer's repos (addelio has it under its ADR-0030 §F). Quail's ADR-0024 only said a PR *carries* a bump, so 142 of the first 154 PRs folded it into the change's commit. Keeping it separate means the change and the release step can be read, reverted or cherry-picked on their own, and re-bumping after `main` moves is a commit of its own. `task version:last-commit` checks the PR's head commit in the `version` workflow: it fails on any other file, a missing `project.yml` or `CHANGELOG.md` change, or a merge as the last commit. The arena-ratings workflow now commits its change and then the bump. Dependabot's bump workflow already did.
